# RAG Project Context

Use this document as context when asking an AI assistant to help with this project. It describes the current files and status; check the actual code before proposing or making changes because the project may have changed since this was written.

## Project Goal

Build a small Retrieval-Augmented Generation (RAG) application in JavaScript. It should load a PDF, index its contents in a vector database, retrieve the most relevant passages for a user's question, and use a language model to answer from those passages.

## Current Project Files

- `main.js`: Node.js ES module. Creates the Pinecone and Mistral embedding clients. The active code embeds one hard-coded question, queries Pinecone for three matches, and prints the query vector and results.
- `rag_test_document.pdf`: Example source document. It describes RAG, document loading, chunking, embeddings, vector databases, retrieval, and generation.
- `test.json`: Example Pinecone query response with three matches. It contains IDs, similarity scores, and matching text, but does not record the question that produced those results. The current code does not write this file; it only prints JSON to the console.
- `.env`: Local credentials. Keep this file private and never paste its values into an AI chat, source control, or public issue.
- `package.json` / `package-lock.json`: Node project configuration and dependency versions.

## Technology Used

- Node.js v22.14.0; JavaScript ES modules and top-level `await`.
- `pdf-parse` (`PDFParse`) for extracting PDF text.
- `@langchain/textsplitters` (`RecursiveCharacterTextSplitter`) for dividing text into chunks.
- `@langchain/mistralai` (`MistralAIEmbeddings`) with model `mistral-embed` for creating vectors for both document chunks and questions.
- `@pinecone-database/pinecone` (`Pinecone`) SDK v9 for storing and querying vectors.
- `dotenv` for loading local environment variables.
- Node's built-in `fs` module for reading the PDF.

The code expects these environment variable names in `.env`:

```env
PINECONE_API_KEY=your-private-pinecone-key
MISTRAL_API_KEY=your-private-mistral-key
```

Use real values only in the local `.env`; do not include them in prompts or documentation shared outside this machine. The Pinecone index named `rag-learning` must already exist, and its vector dimension and metric must be compatible with the embeddings being used.

## Implemented Now

The active code in `main.js`:

1. Loads `.env` and initializes Pinecone for index `rag-learning`.
2. Initializes Mistral embeddings using `mistral-embed`.
3. Embeds the hard-coded question `What is the retrieval?`.
4. Queries Pinecone with that vector using `topK: 3` and `includeMetadata: true`.
5. Prints the embedding vector and serialized Pinecone results.

The `test.json` example has these scores:

- `doc-0`: `0.754645526`
- `doc-4`: `0.748819768`
- `doc-5`: `0.73759228`

These are vector similarity scores, not confidence percentages. `doc-4` appears to contain the most directly relevant retrieval explanation among these matches. Since `test.json` does not store the query, do not assume it was generated by the current hard-coded question without rerunning and checking.

## Present in Code but Not Running

The PDF ingestion code is currently commented out in `main.js`. It sketches these steps:

1. Read `rag_test_document.pdf`.
2. Parse the PDF and extract its text.
3. Split the text into 500-character chunks with zero overlap.
4. Embed every chunk using Mistral.
5. Upsert records into Pinecone with IDs like `doc-0` and each chunk's text in metadata.

Because this code is commented out, running `node main.js` currently does not parse or index the PDF. It only queries vectors that must already be in Pinecone. The indexing and retrieval flows need to be enabled or separated into clear commands. Consider stable IDs and source metadata so re-indexing documents does not accidentally overwrite chunks from a different document.

## Not Implemented Yet

- A runnable PDF ingestion/indexing flow.
- A user-provided question instead of a hard-coded question.
- A chat/generation model call. The current script retrieves passages but does not make an LLM answer from them.
- A prompt that grounds answers in retrieved context and tells the model to say when the context is insufficient.
- A clear answer format with source chunk/document references.
- Writing query, answer, and retrieved matches to a result file such as `test.json`.
- Error handling for missing keys, missing PDF/index, API failures, and empty retrieval results.
- Tests and a useful `npm` script; the current `npm test` is only the default placeholder that exits with an error.

## Suggested End-to-End Flow

1. **Ingest:** Parse the PDF, split it into chunks, create embeddings, and upsert vectors plus text and source metadata to Pinecone.
2. **Ask:** Accept a question, create its embedding, and retrieve the top relevant chunks from Pinecone.
3. **Generate:** Send the question and retrieved text to a Mistral chat model. Tell it to answer only from the supplied context and to say when the context does not support an answer.
4. **Return:** Print or save the answer, the question, and the retrieved sources/scores. Treat scores as similarity measurements, not probabilities.
5. **Verify:** Test ingestion, retrieval, empty matches, API/configuration failures, and whether answers are supported by the returned passages.
